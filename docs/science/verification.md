# Mathematical verification

Run the independent math crate tests without a renderer:

```powershell
cargo test -p earth-math
```

The application starts with analytic WGS84 `h=0` and height-free regional, native-WBM and coarse global categories. Optional downloaded Copernicus elevations activate the source-post triangle surface and explicit reference fallback described in [topography.md](topography.md). Historical fixed terrain/imagery assets remain separate regression coverage. There are implementation and independent-review tests for these models:

1. `tests/geometry.rs` contains implementation-team validation: a published GeographicLib fixture, a grid of ECEF/geodetic roundtrips, poles, date line, negative heights, high altitudes, input rejection, exact unit factors, eye-to-ground range, ray direction scaling, lens roundtrips, flight speed and collisions, and archived texture registration.
2. `tests/review.rs` contains separately authored review tests, including an EPSG/IOGP published coordinate example and independent high-precision algebraic fixtures. The independent reviewer checks the mathematics and adds adversarial cases.
3. `tests/terrain_assets.rs` checks archived source-backed patches with test-local observers, both projection modes and archived Web Mercator registration.
4. `tests/terrain_review.rs` independently checks analytic plane intersections, scaled/parallel/backward/grazing rays, shared edges, BVH versus brute-force traversal, negative-height terrain, ellipsoid-root masking, collision, exact navigation, binary format, image registration and bilinear color filtering.
5. `tests/observation_review.rs` independently checks native geoid decoding and interpolation, malformed grids, vertical height signs, posture and standing headroom, analytic and oblique ellipsoid tangents, terrain angular skyline, negative coastal boundary estimates, and physical-pixel/layout behavior.
6. `tests/astro_review.rs` independently compares SPK positions/velocities with CSPICE, text-PCK body axes with NAIF, UTC/TT and TDB with ERFA, and verifies light time, aberration, Earth-orientation coverage, clock rejection and celestial sight ranges.
7. `tests/rendering_review.rs` independently checks GPU coordinate frames, finite LOD error criteria, fixed ground anchors, date-line/pole placement, curved grass geometry, bounded wind/fade and shared uploaded-triangle ranges. Optical shader equations also receive independent source and native-image review. A separate library-unit fixture checks six complete terrestrial-orientation matrices against Python ERFA.
8. `tests/reference_frames_review.rs` checks complete camera axes, nonrotating transport, reverse time, explicit Cartesian rotations, IERS consistency, edit/relock/crouch behavior, coordinate limits and transactional collision rejection.
9. `tests/guides_review.rs` compares the sampled outline with an independently derived WGS84 tangent cone, checks the ruler's plane and projected endpoints, narrow terrain, unavailable cases, both lenses, roll and physical-pixel scaling. `tests/geodesic_review.rs` adds analytic arcs, an independent meridian integral, PROJ comparisons and geographic edge cases.
10. `tests/water_review.rs` checks classified triangle identity through BVH reordering, unchanged geometry and ranges, negative-height ocean navigation, malformed companions, disjoint canonical render meshes, grass exclusion and independently verified archived face counts.
11. `tests/shoreline_review.rs` uses an independently constructed Cartesian pyramid and split edge to check appended vertices, complete canonical bounds, BVH/ground queries, material partition, malformed irregular connectivity, nonrotating clearance and visible-outline seeding.

Roundtrip tests alone cannot establish correctness: the same error in forward and reverse algorithms could cancel. Published examples and independently calculated expected values address that failure mode.

## Optical performance investigation

This investigation is separate from the delivered midpoint-solver evidence below. The [numerical design record](optical-integrator-review.md) describes diagnostic methods and their safeguards; passing a clear-ray experiment does not authorize changing production contacts or establish smooth flight.

Tangent rays require special treatment because the mathematical problem is ill-conditioned. ### Angular disks versus spherical integration

[`verify_eclipse_disk_error.py`](../../scripts/verify_eclipse_disk_error.py) independently integrates the actual overlap of two spherical caps. In solar-centered polar coordinates it uses the azimuthal interval selected by the Moon-cap dot-product inequality, with `sin(θ)` as the solid-angle measure. Multiplying this integrand additionally by `cos(θ)` computes uniform-radiance flux projected onto a plane perpendicular to the solar-center direction. These two reference quantities have different normalizations; neither includes limb darkening or an atmosphere.

The 459-case sweep uses solar angular radii 0.0045, 0.00465 and 0.0048 rad, lunar/solar radius ratios from 0.9 through 1.1, and contact/interior separations. The largest sampled difference from the angular-plane area is **`8.775×10⁻⁷` of the solar disk for spherical solid angle** and **`1.280×10⁻⁶` for projected uniform-radiance flux**. Doubling Gaussian quadrature from 256 to 512 nodes changes a result by at most `3.45×10⁻¹⁵` in this sweep. The integrals, measures, endpoint substitution and reported results were independently reviewed. This quantifies the approximation on the sampled Earth-viewing domain; it is not a proof for every geometry, particularly close approaches to the Moon.

## Reproducible frame pacing

Run a native build with `--frame-capture artifacts/timing.json`, separately from screenshot mode. Collection begins only after both 120 application frames and 10 seconds have elapsed since the requested presentation became ready. Preparation that becomes pending before collection resets both thresholds. The interval that crosses the warmup boundary is excluded. The next complete intervals are recorded until their sum reaches at least 20 seconds, retaining the final complete interval. This is intended to exclude initial preparation; any later compilation, upload or scheduling cost remains measured.

The JSON preserves every positive finite `Time<Real>` interval, the actual adapter and window presentation mode, physical dimensions, build profile, camera/projection, surface/grass quality, boundary/UI/panel flags and astronomical clock settings. It also reports view changes, unfocused frames and incomplete-scene frames. If the view changes, focus is lost or presentation becomes incomplete during recording, all intervals remain in the data and the analyzer marks the result ineligible as a stationary-scene baseline. These are application frame intervals, including scheduling and presentation pacing; they are not GPU timestamp queries or a universal hardware benchmark.

Run `python scripts/analyze_frame_capture.py artifacts/timing.json` for the summary. With `n` intervals and total time `T`, aggregate throughput is `n/T`, rather than the mean of reciprocal frame times. Mean and median intervals are reported alongside nearest-rank percentiles: the 95th and 99th percentiles select sorted one-based ranks `ceil(0.95n)` and `ceil(0.99n)`. Three Rust tests cover warmup, readiness resets and complete-interval collection; four independent Python test groups cover closed-form statistics, rank boundaries, malformed-data rejection and complete ordered interval accounting for the view-motion phases. The mathematics lead independently reviewed the collection and analysis methods.

Preparation and warmup have a 300-second application-time watchdog: failure to start recording exits with an error. This is an automation bound, not a performance requirement or an exclusion of slow recorded frames.

For opt-in native movement integration, add `--frame-capture-motion` to a `--coast --paused --frame-capture artifacts/motion.json` run. After ready warmup, the probe calls the existing canonical `TerrainScene::fly` API to lift 5 m and request 120 m of forward travel, respecting its 0.25-second input limit. It requires an actual origin rebase and more than 80 m of eye displacement, waits for recovery, changes quality, disables grass after observing the new generation, checks that visible/query counts are cleared, then re-enables grass and waits for two seconds of ready recovery. The probe logs eye/origin coordinates, generations, blade/bound counts and readiness events; it also requires observing pending work.

Motion runs are explicitly labeled `nonstationary-motion-qa` and are never eligible as stationary baselines. They retain all raw intervals, continue beyond 20 seconds when necessary to finish recovery, and exit with an error if the motion sequence exceeds 180 seconds. This validates native state transitions and matched geometry/query counts; it is not a pixelwise GPU comparison or proof that all possible interleavings are covered.

For the separate zoom/ascent probe, use `--frame-capture-view-motion` with `--coast --paused --frame-capture artifacts/view.json`. It applies four seconds each of zoom-in and zoom-out commands at four wheel lines per second, then four seconds of local-up flight at 250 m/s, through the existing lens and canonical-flight APIs. Input time is capped at 0.25 s per update, but recorded frame intervals are never capped or discarded. The probe then requires three continuous seconds of ready presentation and records the attained FOV and eye heights. Its `nonstationary-view-qa` label prevents stationary-baseline eligibility; completion is a state-transition check, not a speed guarantee. The analyzer independently reconstructs each phase from the raw intervals, verifies every interval occurs once in the same order, and assigns it to the preceding frame's action. Phase wall time can therefore differ from command time. The [paired native results](../development/validation.md#asynchronous-terrain-presentation-nearby-markers-and-tape-overlay) disclose focus, pending work, different dwell proportions and remaining stalls.
